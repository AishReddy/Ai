Benefits of RAG

Why use RAG?

🧠

Reduce Hallucination

Answers are grounded in retrieved documents, not fabricated from model weights.

📡

Keep Knowledge Up-to-date

Update the knowledge base without retraining the model — just refresh your documents.

💰

Cost Effective

No expensive fine-tuning. Add or change domain knowledge by editing the vector store.

🔒

Maintain Data Privacy

Only the chunks relevant to a query are passed to the LLM — your full dataset stays private.

🛡️

Privacy: Access Only What's Needed

RAG enforces a kind of least-privilege for AI. The model only ever sees the specific document chunks retrieved for a query — not your entire database. A customer asking about their delayed flight sees only their booking data, not everyone else's.

The RAG Pipeline — Part 1

Ingestion Pipeline

Offline / One-time

Building the Knowledge Base

1
Extract Data

Load documents — PDFs, text files, web pages — and extract raw text.

2
Split into Chunks

Break text into smaller, compressed pieces (Chunk 1, Chunk 2 …). Chunk size is a tuning parameter.

3
Embed → Convert to Numbers

Each chunk goes through an Embedding API → becomes a vector (array of numbers that encodes meaning).

4
Store in Vector DB (Knowledge Base)

Embeddings + original doc chunks stored in a semantic index. Tools: ChromaDB, Pinecone, FAISS, Azure AI Search

The RAG Pipeline — Part 2

Retrieval Pipeline

At Query Time

Finding & Using Relevant Chunks

1
Embed the User Query

The user's question is converted to a vector using the same embedding model.

2
Search the Knowledge Base

Compare query vector against stored embeddings to find the most relevant chunks.

3
Inject Context + Generate

Top chunks are added to the LLM prompt as context. The LLM generates a grounded answer.

Search Strategies

How retrieval works

🔑
Keyword Search

Matches exact words. Like SQL LIKE or MySQL full-text search. Fast but misses synonyms and intent.

🔮
Semantic Search

Compares meaning via embeddings. Finds relevant chunks even with no keyword overlap. Understands context.

🌿
Hierarchical Search

Sentence-level within a topic, switching when a new topic emerges. Respects document structure and boundaries.

Tech Implementation Pillars

Chunking Strategies

📦
1. Fixed-size Chunking

Splits text into equal-sized blocks (e.g. 256 or 512 tokens) with optional overlap between chunks to avoid cutting off context.

🌿
2. Hierarchical Chunking

Creates parent and child chunks. Small child chunks are retrieved for precision; large parent chunks are returned for full context.

🧠
3. Semantic Chunking

Groups sentences by semantic similarity. A new chunk starts when the topic shifts — respects meaning, not just character count.

Tech Implementation Pillars

Vector Databases

Store embeddings + doc chunks. Enable fast similarity search (Top-K retrieval). Also pair with traditional DBs like MongoDB or MySQL for metadata filtering.

🟠
ChromaDB

Lightweight, local-first. Great for prototyping and small projects.

⚡
FAISS

Facebook's library. Blazing fast in-memory vector search. No persistence out of the box.

🌲
Pinecone

Fully managed cloud vector DB. Production-ready with filtering and namespacing.

🔍
Elastic

Combines keyword + vector search. Good for hybrid RAG in enterprise environments.

☁️
Azure AI Search

Microsoft's managed solution. Integrates with Azure OpenAI for end-to-end RAG.

🗄️
MongoDB / MySQL

Used alongside vector DBs for structured metadata — filter by date, user, category before semantic search.

RAG Architecture & Use Cases

Types of RAG Architecture

Architecture Retrieval Type Use Cases
Naive / Standard RAG Vector only FAQs, Chatbots
Hybrid RAG Vector + Keyword Enterprise Search, E-commerce
RAG with Memory Contextual Memory Support assistant / Chatbots
Graph RAG Graph-based Legal / R&D / Knowledge-heavy systems
Agentic RAG Multi-step + Tools Investigations, complex multi-hop queries
Multimodal RAG Text, Image, Video, Audio Visual Q&A (medical, security)
Self-RAG Reflective Regulated domains
🔁

RAG with Memory

Standard RAG is stateless — it forgets past conversations. Adding a memory layer stores conversation history so the LLM can reference earlier turns and give coherent multi-turn answers.

🕸️

Graph RAG — neo4j

Data is stored as a knowledge graph. Entities become nodes; Relations become edges. Runs graph-based + vector-based retrieval in parallel. Best for legal, R&D, and org-wide knowledge systems where who-knows-who matters.

🤖

Agentic RAG

Agents decompose a complex query into sub-questions, run multiple RAG retrievals, and synthesise a final answer. Flow: Query → Agents → RAG ↔ Agents → Response. Used for investigations and multi-hop reasoning (e.g. "explain the Gold price hike in 2025 and compare with other metals" splits into: when? why? other metals at that time?).

🪞

Self-RAG

Adds a reflection mechanism. On receiving a query, the model decides: does this need retrieval? If yes → Document Retrieval → Contextual Generation. If no → Direct Generation. Both paths merge into a Final Response. Used in regulated domains where answer quality must be verified.

🖼️

Multimodal RAG

Real-world data isn't just text — it includes images, video, audio, and documents. Multimodal RAG handles all formats, enabling use cases like medical image Q&A, security footage analysis, and audio transcript retrieval.

🔄

The Augmentation Step

After retrieval, the Top-K ranked results become the context injected into the LLM's prompt. "K" is a tunable parameter — more results = richer context but higher token cost. The LLM then generates its final answer grounded in only that retrieved context.
